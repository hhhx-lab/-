> Kuli captures messy service requests, turns them into orders, and gives both customers and operators a cleaner path from first note to final delivery.

Kuli is a full-stack service storefront and order operations system. It combines a public service website, an authenticated customer workspace, an admin order desk, attachment handling, in-app notifications, a Markdown-powered help center, and the Xiaoku assistant for guided intake and service Q&A.

The project is built as a Nuxt 4 / Vue / TypeScript frontend plus a FastAPI / Python backend, with generated OpenAPI contracts keeping the two sides aligned.

## The 30-Second Version

| What Kuli handles | What the product gives back |
|---|---|
| A visitor who cannot explain a request clearly | A guided service site, detail pages, help center, and note intake path |
| A customer who has placed an order | A personal order desk with status, messages, attachments, quotes, payment, and deliverables |
| An operator managing fulfillment | An admin console for status, priority, quote, cost, profit, replies, attachments, payments, and delivery records |
| A knowledge-heavy support flow | Shared Markdown docs for the help center and Xiaoku RAG-style answers |
| A frontend/backend contract that can drift | FastAPI OpenAPI export consumed by the Nuxt app as generated TypeScript types |

## Service Surface

Kuli is designed around practical service verticals that need flexible intake instead of rigid product SKUs.

| Service area | Examples the site can present | Why it matters |
|---|---|---|
| Document processing | PPT creation, Word formatting, academic formatting, OCR, image-to-Word, PDF cleanup, document rewriting | Customers can send messy files first and let the team choose the right production path |
| AI tool setup | ChatGPT, Gemini, Claude, Grok, Telegram, Google accounts, subscriptions, API keys, Claude Code, Codex, Cursor, Antigravity, relay services | Turns confusing overseas AI tooling into a guided setup workflow |
| Custom tool development | Websites, mini programs, crawlers, demos, apps, databases, agents, internal tools, design systems | Lets customers bring an idea and treat Kuli as a technical delivery team |
| Deployment and configuration | VPN, server deployment, website deployment, domain setup, bastion hosts, subnet planning, server management, cloud compute rental | Gives infrastructure requests a clear intake, quote, and delivery trail |

The public service routes also support product/tool discovery, API or token requests, and a catch-all path for requests that do not fit a fixed category.

## Why It Feels Different

| Usual service site | Kuli |
|---|---|
| Static pages and a contact form | Service pages, guided note intake, order state, messages, attachments, and delivery records |
| Operators track work in scattered chats | Admin console with status, priority, quote, cost, payment, delivery, public replies, and internal notes |
| Frontend and backend contracts drift over time | OpenAPI contracts are generated from FastAPI and checked by the frontend workspace |
| Help docs and AI support live separately | Markdown knowledge powers both the document center and Xiaoku retrieval |
| Local setup is a pile of manual commands | `npm run start:local` builds the full local loop and starts API, Web, and worker in tmux |

## Quick Start

Requirements:

- Node.js and npm
- uv for the Python environment
- Docker or OrbStack for Postgres/pgvector and Redis
- tmux and curl for the one-command local runner

Clone the project, install dependencies, copy environment templates, and start the full local stack:

```bash
npm install
uv sync --project apps/api
cp .env.example .env
cp apps/api/.env.example apps/api/.env
cp apps/web/.env.example apps/web/.env
npm run start:local
```

Open:

```text
Web:  http://127.0.0.1:3000
API:  http://127.0.0.1:8000/api/health
Deps: http://127.0.0.1:8000/api/health/deps
```

`npm run start:local` installs Node dependencies, syncs the API environment with uv, starts Postgres/pgvector and Redis, creates the local runtime database, runs Alembic migrations, indexes the knowledge base, checks knowledge health, builds Nuxt, and starts API, Web, and worker sessions in tmux.

View logs:

```bash
tmux attach -t kuli-api
tmux attach -t kuli-web
tmux attach -t kuli-worker
```

Stop everything:

```bash
npm run stop:local
```

Keep Postgres and Redis running while stopping tmux services:

```bash
bash scripts/stop-local.sh --keep-stack
```

Use different local ports when needed:

```bash
API_PORT=8010 WEB_PORT=3010 npm run start:local
```

Use a separate local database:

```bash
KULI_LOCAL_DB_NAME=kuli_runtime_dev2 npm run start:local
```

## Development Commands

Start API and Web in hot-reload mode:

```bash
npm run dev
```

Start each side manually:

```bash
PYTHONPATH=apps/api uv run --project apps/api uvicorn app.main:app --reload --reload-dir apps/api/app --reload-dir apps/api/alembic --host 0.0.0.0 --port 8000
npm run dev --workspace @kuli/web
```

Run migrations and the worker:

```bash
npm run db:migrate
npm run worker
```

Run the usual checks:

```bash

npm run typecheck
npm run test
npm run build
```

Run browser smoke after a local server is already running:


## Environment

Environment values are template-driven. Copy the templates, then edit local `.env` files only on your machine or in your deployment secret manager.

```bash
cp .env.example .env
cp apps/api/.env.example apps/api/.env
cp apps/web/.env.example apps/web/.env
```

Important groups:

| Group | Variables |
|---|---|
| Runtime | `APP_ENV`, `APP_SECRET_KEY`, `ACCESS_TOKEN_EXPIRE_MINUTES` |
| Database and queue | `DATABASE_URL`, `REDIS_URL` |
| Frontend public config | `NUXT_PUBLIC_API_BASE_URL`, `NUXT_PUBLIC_SITE_URL`, `NUXT_PUBLIC_APP_NAME`, `NUXT_PUBLIC_ENABLE_XIAOKU` |
| Object storage | `OBJECT_STORAGE_PROVIDER`, endpoint, bucket, region, local dir, access key, secret key, public base URL, presign expiry |
| AI and retrieval | `LLM_PROVIDER`, `LLM_MODEL`, `LLM_API_KEY`, `LLM_BASE_URL`, `OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_BASE_URL`, `EMBEDDING_MODEL`, `VECTOR_DIMENSION`, `KNOWLEDGE_ROOT` |
| Email and notifications | `MAIL_PROVIDER`, sender, reply-to, SMTP host, port, username, password, timeouts, retry limits |
| Safety limits | `MAX_REQUEST_BODY_BYTES` |

Use a strong generated `APP_SECRET_KEY` outside local development:

```bash
openssl rand -hex 32
```

Do not commit `.env`, real API keys, SMTP credentials, object storage credentials, local proxy settings, generated uploads, `.codex`, or debug artifacts.

## Knowledge and Xiaoku

The help center and assistant share the same Markdown source folder:

```text
apps/api/knowledge/docs
```

After editing knowledge articles, rebuild and inspect the index:

```bash
PYTHONPATH=apps/api uv run --project apps/api python scripts/index_knowledge.py
PYTHONPATH=apps/api uv run --project apps/api python scripts/knowledge_doctor.py
```

Published documents should include frontmatter for slug, title, description, tags, order, updated date, and status. The frontend and Xiaoku only publish documents marked as published.

## Production Notes

For staging or production, plan for:

| Need | Guidance |
|---|---|
| Domain configuration | Set the public site URL, API base URL, and CORS origins to the real domains |
| Secrets | Generate a strong app secret and keep API keys, SMTP credentials, and storage credentials in a secret manager |
| Data services | Use Postgres + pgvector and Redis rather than lightweight local fallbacks |
| Storage | Use a private S3, R2, or OSS bucket with least-privilege credentials and short-lived signed access |
| Email | Configure and test a real SMTP or email provider for verification, reset, and order updates |
| AI and embeddings | Use real provider keys only when remote LLM and embedding behavior is intended |
| Admin accounts | Do not rely on local demo seed accounts for production access |
| Verification | Run migrations, contract checks, type checks, API tests, build, production-stack verification, and a manual end-to-end order flow |

## Boundaries

- Kuli is a service-order operations system, not an automatic fulfillment engine. Human review, pricing, payment confirmation, and delivery decisions still matter.
- Payment QR flows are manual unless a real payment provider callback is integrated and tested.
- AI features can use local rule-based fallbacks when remote model keys are missing. Remote LLM, embedding, and relay behavior depends on configured providers.
- Crawlers, account setup, deployment automation, and AI tool configuration should be used only with authorization and within the target service rules.
- User uploads and deliverables should be handled through private storage, short-lived links, and clear file retention policies.
- Generated content, document formatting, and assistant answers still need human review before public or client delivery.

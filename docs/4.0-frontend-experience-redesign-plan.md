# 酷里 4.0 前端体验重设计规划

## 1. 背景

当前酷里已经完成 Vue 3 + Nuxt + FastAPI 的前后端分离迁移，也具备服务详情、文档中心、小纸条、订单工作台、管理员后台、个人主页和小酷 Agent 等核心功能。但前端体验还停留在“功能可用”的阶段，整体视觉语言、排版层级、页面结构和业务引导都不够成熟。

这份文档用于把当前前端槽点整理成可执行的 4.0 UI/UX 升级方案。目标不是简单“换皮”，而是让官网、文档中心、下单流程、订单工作台和后台管理都更像一个可以正式对公众发布的服务平台。

## 2. 当前仓库事实

- 首页使用 `hero + section + grid + card` 的连续结构，服务展示和流程说明都靠同一套卡片承载，页面变化有限：`apps/web/app/pages/index.vue:2`、`apps/web/app/pages/index.vue:22`、`apps/web/app/pages/index.vue:54`。
- 文档中心首页当前仍叫“酷里知识库”，采用顶部大标题 + 左侧搜索面板 + 右侧卡片结果流，尚不是正式文档中心的信息架构：`apps/web/app/pages/help/index.vue:2`、`apps/web/app/pages/help/index.vue:12`、`apps/web/app/pages/help/index.vue:30`。
- 文档详情页已经有左侧文档目录、正文和右侧目录的三栏雏形，但 Markdown 渲染由页面内手写 `markdownToHtml` 完成，只支持标题、无序列表和段落，无法稳定处理表格、代码块、引用、链接、强调、嵌套列表等内容：`apps/web/app/pages/help/[slug].vue:2`、`apps/web/app/pages/help/[slug].vue:25`、`apps/web/app/pages/help/[slug].vue:73`。
- 小纸条页面为左侧提示、右侧表单的双栏布局，但左栏只是 tips/notice，缺少动态服务上下文、材料清单、文件上传引导和小酷辅助入口：`apps/web/app/pages/note.vue:8`、`apps/web/app/pages/note.vue:23`。
- 用户订单详情页以多个 `info-card` 线性堆叠呈现，进度、沟通、附件、报价、付款、交付物没有形成强工作台结构：`apps/web/app/pages/orders/[orderNumber].vue:9`、`apps/web/app/pages/orders/[orderNumber].vue:24`、`apps/web/app/pages/orders/[orderNumber].vue:35`。
- 管理员列表已有搜索栏和筛选控件，但视觉上仍是工具条 + 卡片网格，没有形成高密度后台管理台：`apps/web/app/pages/admin/index.vue:11`、`apps/web/app/pages/admin/index.vue:45`。
- 全局 CSS 使用统一深色背景、圆角卡片、超大标题、霓虹绿色强调色和通用 `.section/.card/.panel`，容易导致页面观感重复：`apps/web/app/assets/css/main.css:1`、`apps/web/app/assets/css/main.css:34`、`apps/web/app/assets/css/main.css:168`。

## 3. 核心问题归纳

### 3.1 页面布局重复

现在很多页面都像同一个模版换文案：顶部大字 + 小字 + 卡片。它适合早期原型，但正式发布时会显得“每页都在自我介绍”，用户无法快速判断当前页面到底是官网、文档、表单、订单还是后台。

需要建立多种页面骨架：

- 官网首页：品牌叙事 + 服务入口 + 信任内容 + 案例/规则，应该有更强的视觉记忆点。
- 服务详情页：面向决策，重点是适合谁、交付什么、材料、价格周期、风险边界和下单入口。
- 文档中心：面向阅读和检索，应该是文档型布局。
- 小纸条：面向输入和被引导，应该是任务型布局。
- 我的订单：面向状态理解和下一步行动，应该是工作台布局。
- 管理后台：面向筛选、处理、批量判断，应该是高密度管理台布局。
- 个人主页：面向账号状态和快捷入口，应该是用户中心布局。

### 3.2 排版不适合长时间阅读

当前 `body` 默认 `font-weight: 600`，正文整体偏重；`h1/.mega` 使用非常大的标题尺寸，很多内页也继承了英雄页级别的视觉重量。正式页面应该有更细的字号阶梯和阅读节奏。

建议：

- 正文默认字重降到 400/450，重要标签和按钮再加粗。
- 中文正文行高提高到 1.7 左右，长文档正文最大宽度控制在 680-760px。
- 标题分层：官网首屏可以大，文档/表单/后台不使用 hero 级标题。
- 内页标题避免每页都是 `mega`，改成 page title、section title、panel title 三档。
- 中英文、数字、状态码、金额和时间要有统一格式，避免页面像数据库字段直出。

### 3.3 文案和 Markdown 渲染不稳定

目前页面里出现英文状态、内部字段、source 标识、placeholder 式文字和 Markdown 解析不完整的问题。用户看到 `submitted`、`service:xxx`、`storageKey`、`metadata` 这类字段，会觉得平台半成品。

需要统一做三类清理：

- 用户可见字段映射：订单状态、付款状态、附件扫描状态、服务 slug、source key 都要映射成中文业务文案。
- Markdown 渲染：替换手写 parser，使用成熟 Markdown 渲染链路，并启用安全白名单。
- 空状态和占位符：所有“暂无”“未填”“metadata”必须换成业务语气，并提供下一步动作。

### 3.4 文档中心定位不清

“知识库”这个名字偏内部，用户更容易理解的是“文档中心”或“帮助中心”。这里不只是搜索卡片，而应该是酷里业务知识的公开入口，也是小酷 RAG 的来源。

文档中心应包含：

- 快速开始：第一次来怎么问、怎么写小纸条、什么时候需要登录。
- 核心概念：小纸条、订单状态、定金、尾款、验收、交付物、附件、安全边界。
- 服务指南：AI 工具、文档处理、小工具开发、部署配置、API/token、无法分类需求。
- 常见问题：价格、付款、修改、售后、材料、回复时间、不能做什么。
- 法律与规则：隐私政策、服务条款、上传说明、安全说明。
- 联系我们：联系渠道、回复时间、紧急需求说明。

### 3.5 小纸条缺少“被陪着填写”的感觉

现在小纸条页面左边是静态提示，右边是表单，用户仍然要自己理解所有字段。它应该更像“需求整理台”：根据服务类型、用户输入和小酷建议逐步把模糊需求变成可提交信息。

需要让左侧区域承担更多价值：

- 当前所选服务的材料清单。
- 小酷提示和“帮我整理”入口。
- 示例小纸条随服务类型变化。
- 文件/截图上传入口和安全提醒。
- 提交前摘要预览。

### 3.6 订单和后台没有工作台感

普通用户关心的是“现在到哪一步、我要做什么、有没有报价、能不能验收”。管理员关心的是“哪些订单最急、哪些卡住、谁负责、风险在哪里、下一步怎么维护”。现在两者都以卡片堆叠为主，信息优先级不够清晰。

需要分离两套体验：

- 用户订单工作台：状态头部、下一步行动、进度时间线、沟通、附件、报价付款、交付验收。
- 管理员订单管理台：搜索筛选、列表/表格、状态批处理、AI 建议、内部字段、客户可见信息、审计记录。

### 3.7 个人主页和账号入口不自然

右上角账号菜单方向是对的，但个人主页、设置、邀请、通知目前像几个功能页拼起来。需要把它改成自然的用户中心：右上角显示头像/邮箱/未读，点开后进入明确的“我的酷里”空间。

## 4. 4.0 设计目标

1. 让每类页面拥有不同的布局骨架，避免所有页面都像同一套卡片模板。
2. 建立适合中文阅读的字体、字号、行高、段落和状态文案规范。
3. 把文档中心做成可阅读、可检索、可被小酷引用的知识系统。
4. 把小纸条从“普通表单”升级为“需求整理流程”。
5. 把订单页从“信息堆叠”升级为“客户下一步工作台”。
6. 把管理员页从“卡片列表”升级为“高密度订单运营后台”。
7. 清理所有内部字段直出、占位符、Markdown 渲染异常和重复文案。
8. 保持小酷存在感，但不能遮挡业务流程或替代核心页面设计。

## 5. 视觉方向建议

### 5.1 总体气质

酷里不是传统 SaaS，也不是纯客服系统。更适合的方向是“聪明的小窗口工作室”：轻松、机灵、可信，有一点工具感和手作感，但发布给公众时必须干净、稳定、有秩序。

建议采用：

- 深色品牌底保留，但不要全站都沉在黑绿卡片里。
- 文档中心和表单页可以使用更高对比的阅读底色或浅色内容区。
- 强调色从单一荧光绿扩展为功能色体系：绿色用于确认、蓝色用于信息、琥珀用于待处理、红色用于风险。
- 页面背景减少装饰性发光，增加真实界面质感：侧栏、分割线、表格、步骤条、文档阅读区。
- 卡片圆角收敛到 8-14px，后台和表单区域更克制；小酷、首页局部和营销内容可以更活泼。

### 5.2 页面差异化原则

- 首页：可以更有品牌记忆点，用服务雷达、真实问题流、窗口式演示、案例条、规则对照等组合。
- 服务页：使用“问题-判断-材料-交付-价格周期-风险-FAQ-CTA”的纵向服务说明，不只是卡片。
- 文档中心：左侧目录 + 中间正文 + 右侧本页目录/小酷提问，不使用大面积营销卡片。
- 小纸条：左侧动态助手/材料清单，右侧分步表单，中间或底部有需求摘要。
- 订单页：顶部状态仪表盘 + 左侧时间线 + 右侧下一步/付款/附件/交付。
- 后台：表格优先，列表密度更高，右侧详情抽屉或详情页承载维护动作。
- 个人页：账号信息、订单概览、积分邀请、通知设置用自然 dashboard，而不是分散孤岛。

## 6. 页面级改版规划

### 6.1 首页

目标：从“服务卡片集合”升级成“用户一眼知道这里能帮他解决什么”的服务入口。

建议结构：

1. 首屏：保留酷里小窗口概念，但用真实交互窗口或动态需求流，而不是单纯大标题。
2. 服务入口：不要全是同尺寸卡片，改成主服务大模块 + 快捷问题标签 + “不知道选哪个”入口。
3. 判断逻辑：展示酷里如何判断能不能做、需要哪些材料、什么情况下不接。
4. 交易规则：用对照表说明咨询、报价、定金、尾款、验收、售后。
5. 案例流：用小型案例条展示“用户问题 -> 酷里判断 -> 交付结果”。
6. 小酷入口：提供“帮我选服务”“帮我写小纸条”的轻量 CTA。

验收标准：

- 首页至少使用 4 种不同的信息组件，而不是连续卡片网格。
- 首屏下方能露出下一段内容，避免只看到大标题。
- 所有 CTA 指向明确：看服务、写小纸条、问小酷、读文档。

### 6.2 服务详情页

目标：服务页要像正式服务说明，而不是“扩展卡片”。

每个服务详情建议固定结构：

- 服务判断区：这个服务适合谁、不适合谁。
- 常见需求区：用户常说的问题。
- 交付物区：最终可能拿到什么。
- 材料准备区：截图、文件、链接、账号类说明、安全提醒。
- 价格与周期区：只给参考范围和影响因素，不承诺固定价。
- 风险边界区：做不了什么、需要管理员确认什么。
- 案例区：示例需求和处理方式。
- FAQ 区：该服务专属问题。
- CTA 区：带服务类型进入小纸条，或让小酷先判断。

验收标准：

- 服务页不再只靠卡片堆叠表达内容。
- 从服务详情页进入 `/note` 时能带入服务类型，并显示专属提示。
- 服务页内容可以被文档中心和小酷知识库复用。

### 6.3 文档中心

目标：把“知识库”正式改造成“文档中心”，成为公开帮助文档和小酷知识库的统一来源。

信息架构：

- 路由建议：保留 `/help`，新增 `/docs` alias 或把导航文案改为“文档中心”。这样不破坏现有路径，又减少“知识库”内部感。
- 左侧：文档分组导航，包括快速开始、核心概念、服务指南、常见问题、规则与条款、联系我们。
- 中间：Markdown 正文阅读区。
- 右侧：本页目录、小酷提问入口、相关文档、更新时间。
- 顶部：文档搜索、热门问题、最近更新。

技术改造：

- 用 `markdown-it`、`remark/rehype` 或 Nuxt Content 类似方案替代页面内手写 `markdownToHtml`。
- 支持标题、链接、强调、表格、代码块、引用、任务列表、锚点、frontmatter。
- 使用 HTML sanitize，禁止不可信脚本。
- 文档 frontmatter 继续服务小酷索引：slug、title、description、category、tags、order、updated_at、status、related_docs。

验收标准：

- `/help` 首页不再是卡片搜索页，而是文档中心首页。
- `/help/:slug` 桌面端为稳定三栏，移动端为目录折叠 + 正文 + 底部相关文档。
- Markdown 表格、链接、列表、代码块都正常渲染。
- 隐私政策、服务条款、上传说明、联系我们能进入同一文档导航体系。

### 6.4 写小纸条

目标：从“右侧乱表单”升级成“需求整理流程”。

建议结构：

- 顶部轻量说明，不使用超大 hero。
- 左侧为动态辅助栏：
  - 当前服务类型。
  - 该服务需要哪些材料。
  - 示例小纸条。
  - 安全提醒。
  - 小酷“帮我整理”入口。
- 右侧为分步表单：
  - 第一步：想解决什么。
  - 第二步：已有材料和上传文件。
  - 第三步：期望交付物。
  - 第四步：时间和预算。
  - 第五步：联系方式和提交确认。
- 底部或右侧浮层显示“小纸条预览”，让用户知道将提交给管理员的内容。

交互建议：

- 用户输入太短时，小酷只提醒一个关键问题。
- 服务类型切换时，左侧材料清单和示例同步变化。
- “让 AI 帮我整理”改成更明确的“小酷帮我整理成给管理员看的版本”。
- 文件上传从订单详情前移到小纸条阶段，至少允许截图/文件作为咨询材料。

验收标准：

- 左侧不再空，只承担服务上下文和材料引导。
- 表单字段有视觉分组，不再像长列表。
- 提交前能看到结构化摘要。
- 用户未登录时给出清晰登录门槛和返回路径。

### 6.5 我的订单

目标：普通用户打开订单页时，第一眼知道“现在状态”和“我下一步该干什么”。

订单列表建议：

- 顶部增加状态筛选：全部、待确认、待补充、待报价、进行中、待验收、已完成。
- 每个订单使用更清晰的信息层级：订单标题、状态、下一步、最近消息、金额/报价、更新时间。
- 空状态提供两个行动：写小纸条、查看服务。
- 订单较多时支持搜索订单号/标题/服务类型。

订单详情建议：

- 顶部状态头：订单号、服务类型、当前状态、下一步 CTA。
- 主体三块：
  - 左侧：进度时间线。
  - 中间：沟通记录和补充材料。
  - 右侧：报价付款、交付物、验收动作。
- 附件区域改成文件列表，显示文件名、类型、大小、上传时间、处理状态、下载动作。
- 报价/付款区域用金额卡和状态标签，不显示内部 key。
- 验收按钮只在可验收状态出现，并附带“通过/需要修改”的明确路径。

验收标准：

- 用户详情页不再是多个等权卡片堆叠。
- 所有英文状态都有中文展示和简短解释。
- “下一步”必须在首屏可见。
- 附件、付款、交付物没有内部字段直出。

### 6.6 管理员后台

目标：从“管理员版卡片页”升级为订单运营后台。

列表页建议：

- 使用表格或高密度列表，不再主要用大卡片。
- 顶部固定搜索栏，支持订单号、客户邮箱、联系方式、需求关键词、附件名。
- 筛选器分组：状态、服务类型、优先级、负责人、付款状态、是否有 AI 建议。
- 列表列建议：订单号、客户、服务、状态、优先级、下一步、最近更新时间、金额、负责人、风险标签。
- 支持保存筛选、快速清空、分页和空结果引导。

详情页建议：

- 顶部为订单概要和关键操作：改状态、分配负责人、运行 AI 建议、发客户消息。
- 左侧为客户可见信息和沟通。
- 中间为订单流程：状态、报价、付款、交付、验收。
- 右侧为内部运营：成本、利润、内部备注、AI 摘要、风险、审计日志。
- 所有客户可见/内部可见字段要用明显标签区分。

验收标准：

- 管理员列表在 20 条订单时仍然可快速扫描。
- 搜索、筛选、分页、状态维护在同一工作流内完成。
- 内部字段不会混入客户可见区域。
- AI 建议可见但不替代人工确认。

### 6.7 个人主页、设置、邀请、通知

目标：把账号相关页面合成自然的用户中心。

导航建议：

- 右上角显示登录邮箱/头像/未读角标。
- 点击后展示账号菜单：个人主页、我的订单、通知中心、设置、积分与邀请、退出登录。
- 管理员账号额外显示“管理后台”。

页面建议：

- `/me` 作为用户中心首页：账号状态、订单概览、积分进度、最近通知、快捷操作。
- `/settings` 聚焦账号设置：展示名、邮箱验证、密码修改、通知偏好。
- `/referrals` 聚焦邀请：邀请码、邀请链接、奖励记录、规则说明。
- `/notifications` 聚焦通知：未读/已读筛选、订单跳转、批量已读。

验收标准：

- 账号入口在右上角清晰可见，不和主要 CTA 抢位置。
- 个人中心各页面拥有统一侧边导航或顶部 tab。
- 积分和邀请不再像临时卡片，而有明确规则和状态。

## 7. 组件与设计系统改造

## 8. 文档与小酷知识库改造

文档中心既给人读，也给小酷用，因此需要统一内容来源。

建议目录：

```text
apps/api/knowledge/docs/
├── quick-start.md
├── concepts.md
├── services/
│   ├── ai-tools.md
│   ├── document-processing.md
│   ├── tool-development.md
│   ├── deployment-config.md
│   ├── api-token.md
│   └── not-sure.md
├── guides/
│   ├── write-a-note.md
│   ├── prepare-files.md
│   ├── order-status.md
│   └── acceptance-and-aftercare.md
├── faq.md
├── legal/
│   ├── privacy.md
│   ├── terms.md
│   └── upload-policy.md
└── contact.md
```

小酷使用规则：

- 回答业务问题时优先引用文档中心内容。
- 不回答与酷里业务无关的问题。
- 遇到价格、成功率、账号密码、付款凭证等敏感问题时使用边界话术。
- 在文档中心页面，小酷应结合当前文档 slug 回答。
- 在小纸条页面，小酷应生成结构化需求摘要。
- 在订单页，小酷只能读取当前登录用户自己的订单摘要。

## 9. 交互与动效原则

- 动效服务于理解，不做无意义漂浮装饰。
- 小酷可以有动作，但在表单、订单、后台和文档阅读时默认收敛。
- 所有 hover、focus、active 状态要稳定，不造成布局跳动。
- 表单错误只提示关键问题，不连续弹多个气泡。
- 后台动效最少，优先响应速度和信息密度。
- 移动端先保证可读和可操作，小酷默认折叠。

## 11. 验收标准

### 视觉验收

- 任意连续打开 5 个页面，不能都呈现“巨型标题 + 小字 + 卡片网格”的同质结构。
- 正文阅读区行宽、字号、行高稳定，中文段落不拥挤。
- 所有按钮、输入框、状态标签、金额、时间格式统一。
- 页面在 375px、768px、1440px 三类宽度下无明显遮挡、溢出和文本重叠。

### 内容验收

- 用户可见页面不出现 `submitted`、`storageKey`、`metadata`、`service:xxx` 等内部字段。
- 文档 Markdown 支持标题、列表、表格、链接、强调、代码块、引用。
- 文档中心包含快速开始、核心概念、服务指南、FAQ、法律条款、联系我们。
- 小酷回答和文档中心内容不冲突。

### 流程验收

- 游客能自然浏览首页、服务页、文档中心，并理解登录后才能写小纸条和看订单。
- 登录用户能完成：写小纸条、查看订单状态、补充沟通、上传附件、查看报价付款、验收交付。
- 管理员能完成：搜索订单、筛选状态、查看详情、更新状态、发公开消息、记录报价付款、查看 AI 建议。

## 12. 风险与注意事项

- 文档中心改造会影响小酷知识库，需要保证前端展示、后端索引和 Agent 引用同源。
- Markdown 渲染要做 sanitize，不能因为支持 HTML 而引入 XSS 风险。
- 管理员后台不能把内部备注、成本、利润暴露到普通用户页面。
- 小酷视觉和对话能力不能掩盖核心页面问题；它是辅助层，不是替代页面设计的补丁。
- 视觉升级要分阶段落地，避免一次性改完整站导致功能回归难定位。

## 13. 推荐下一步

先从 Phase 1 + Phase 2 开始：统一排版、状态映射和 Markdown 渲染，然后重做文档中心。原因是它们会影响所有页面，也直接解决“文字不舒服、Markdown 没渲染好、知识库不像文档中心、小酷知识不统一”这几个最明显的问题。

随后再做小纸条和订单工作台，因为这两处是转化和留存的核心路径。首页和服务页可以并行设计，但不建议先只做首页美化，否则会变成“门面好看，流程还是半吊子”。
